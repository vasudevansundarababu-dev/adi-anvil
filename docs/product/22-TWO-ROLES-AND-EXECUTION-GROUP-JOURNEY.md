# Two roles and separate execution-group pages

User decision, 31 October 2026, supersedes older Product Owner/multi-role/two-Admin policies.
Only two active access roles exist: **Admin** and **RL Engineer**. Existing Admins stay
Admin; other existing project members migrate to RL Engineer without identity promotion.
Historical memberships, decisions, immutable inputs and audit evidence remain available
as history; they do not constitute additional current roles.

Admin includes engineering and administration. Admin's explicit Run action can authorize
the exact run, model/key versions, rates/terms and aggregate budget; no Product Owner,
second Admin or separate approval ceremony/file is required. Record that exact Admin
authorization immutably and recheck active Admin membership between stages. Roles do not
change identity provenance. User clarification, 31 October: existing Admin accounts are
eligible based on active project role, regardless of seeded origin. No extra account or
invitation is required. Origin metadata remains intact and is recorded in the run audit;
it is not a permission category and never establishes model-performance evidence.
No paid dispatch occurs as part of building this feature. Runtime live controls, exact
explicit budgets, rights confirmation, project and hidden-reference isolation remain.

RL Engineers create/import tasks, configure evaluation selections, run authorized tasks,
inspect results and perform explicitly assigned grading duties. They cannot manage keys,
grant themselves Admin, authorize new paid budget or read unassigned private references.
Reviewer/grader/adjudication assignments are task duties, not additional access roles.

## Separate pages

Model setup requires a provider, model ID and saved key, without manual pricing or
processing-terms references. Anvil manages supported cost estimates internally and
freezes them with each execution group. Unknown or expired cost support blocks paid
dispatch rather than inventing a rate. Existing historical metadata remains preserved.
Admin Run confirms permission to process the task and authorizes its explicit budget.
For a draft using older runtime configuration, **Update configuration** creates a new
group from the same immutable preparation and cap. It does not authorize, reserve or
dispatch anything; the original group remains available. Existing models and presets
do not need replacement merely to supply pricing or processing terms.

1. **Execution groups**: paginated list, status, Open and Create. No creation form inline.
2. **Create execution group**: task/package, execution preset, exact models, explicit budget
   and limits. Create saves immutable preparation/group records, makes no provider call,
   and opens the saved group's separate detail page.
3. **View execution group**: read-only bound task/models/budget, current readiness and Run;
   running/completed groups show per-model states and links to dashboards. No create/edit
   form in the viewer. Changes create new versions through the separate Create page.
4. **Task detail/list**: clear Run action opens group creation with the task preselected;
   task run history and each existing run's Dashboard remain directly available.
5. **Run dashboard**: results/failures, observed trajectories, exact task/rubric/evaluation
   snapshots, usage and compatible comparisons. No fabricated/model-performance fixtures.

Saved preparation links remain read-only compatibility views with a link to Create; they
must not mix a create form, group list and group viewer in the same screen. The classic
comparison remains available with current two-role authorization. Old resource-assignment
field names may be retained internally for immutable history/compatibility, not presented
as current roles or additional approver requirements.

Migration archives current membership rows before changing active roles, retains prior
rows inactive, restricts new active roles to Admin/RL Engineer and preserves all users,
passwords, resource bindings and data. Existing non-Admin users are not promoted to Admin.
Private-reference access remains individually assigned/owned; there is no blanket
private-reference grant to every RL Engineer or Admin.
