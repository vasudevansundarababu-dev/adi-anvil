## 1. Mandate

Build one independent research-asset/evaluation product when implementation is authorized. Own its repository, UI, backend, schema, tests, dependencies, IAM/secrets, artifacts, deployment and release schedule. Do not create an edition switch or a mandatory shared-core package. No sibling repository is required for this product.

The current task creates specifications, not application code or GitHub repositories. Do not start paid calls, cloud deployment, credentials or data transfer from this handoff alone.

## 2. Proposed team responsibilities

Product/design owns local identity, journeys and acceptance priorities. Engineering owns local interfaces, data/state model and operational controls. Research/evaluation owns measurement validity; domain experts own task/reward/domain review. Admin/security owns access and applicable authorization. A delivery owner owns recipient/use scope and customer acceptance; Sales owns discovery and approved communication, not scientific results.

These are responsibilities, not headcount commitments or completed staffing decisions. The two products may choose different stacks and release dates. Reusing an external library does not imply shared deployments or customer data.

## 3. Implementation sequence to review

1. For the confirmed 200-case multi-domain business diagnostic, inspect permitted Bodhium samples, inventory partial inputs, agree the lab requirement profile/interface and name the acceptance owner. KYC and shopping are not the selected first SKU.
2. Implement objective/configuration/data lineage and local role/approval foundations.
3. Implement approved partner/Praxis intake as needed, case gap/enhancement records and research qualification on a representative case sample. Reuse Praxis commissioned SME authoring where supported. Calibrate references/rubrics and qualify the selected harness; build stateful simulation only for interactive cases. Do not force all 200 cases through a KYC/synthetic-only workbench.
4. Implement an approved diagnostic assessment with valid/invalid outcomes, observable traces and failure findings.
5. Generate a traceable reviewed diagnostic report and immutable pack release/delivery.
6. Add one qualified training-asset format, then customer-supplied intervention comparisons.
7. Add external benchmark integration only after source/protocol/rights validation and contract tests.

No model optimizer, H100/Tinker training control, Enterprise deployment or business-monitoring backlog item enters this sequence.

This is a proposed sequence, not a delivery-date, budget or full-release commitment.

## 4. Definition of implementation readiness

For each feature: resolve remaining user choices; define actors/permissions; specify inputs/states/errors; agree version and approval invalidation; list data rights/egress; define test evidence and acceptance threshold; assess dependency readiness; assign owner. No inferred provider capability or “specified = built” shortcut.

Require unit/contract tests for object transitions, authorization, data separation, retries/idempotency and invalidation; integration tests for each declared adapter/interface; end-to-end tests for the selected local journeys; security/privacy review; accessible UI checks; scientific/grader validation where applicable. Document untested limits.
