# Report review policy — user-approved change

The user's November9 instruction replaces the fixed reviewer-count requirement for new report policies. Report review is configurable by an authenticated project Admin in the application. The implemented range is zero through ten reviewers, with a safe default of one. This count governs report authorization; it does not change the three-task/three-candidate/two-repetition matrix or the existing81-point scoring calculation.

An actual authenticated Admin execution requires no additional report reviewer. The execution actor is recorded from current server-side membership, independently from the draft creator: an Admin-created draft executed by an Engineer does not inherit the exemption. An Engineer-created draft actually executed by an Admin does. An explicit authenticated Admin approval can also authorize an exact immutable result hash, including an older report, without manufacturing reviewer decisions.

New version2 protocols use a configurable list of real, distinct individual report duties rather than mandatory first/second/adjudicator stages. Required counts and policy revision/hash are frozen when the protocol or rehearsal is created. Later project settings changes do not rewrite those snapshots. Version1 serialization, hashes, source records and actual historical reviews remain immutable. Admin exact-result authorization is recorded separately, not by rewriting those records.

The API and UI distinguish `admin_run_exempt`, `admin_approved`, `policy_no_review` and actual `reviewed` states. Exemptions and zero-review configuration carry `reviewer_verified=false`. Human reviewers are counted only from actual authenticated, current individual review-duty submissions against the exact stored result; duplicate submissions do not inflate the count.

Report review configuration does not approve source rights, change native qualification, activate providers, reserve or relax spend, or authorize deployment. Paid calls remain off. Official report Admin approval rechecks current source integrity, exact runtime and native qualification; a post-capture qualification revocation blocks new report authorization. A separate fictional software rehearsal is labelled non-model/non-native and never supplies official qualification or model performance.

Validation is recorded in the final QA evidence, with synthetic SQL fixtures explicitly distinguished from native execution. The focused regression set includes configurable counts0/1/4, actual Admin executor versus creator, immutable policy snapshots, spoofed actor/Admin denials, duplicate reviewer retries, exact-hash approvals and report PDF gates. A forward-only063 migration closes malformed internal policy JSON through explicit required-key/type/value/revision/hash checks; it does not expand authority.
